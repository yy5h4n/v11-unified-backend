# Backend Casebook V0

第一条离家门灯case已落实为`d0_contract.py`中的自编公开合同：离家激活后120秒处理两个设备，维持期间外生重开门后60秒恢复；时限按原生公开变化时刻起算，不随LLM等待延后。规则在诊断前确定，修正原因是单步只能操作一个设备，不是迁就模型失败。已有原生门灯同时需处理的可行性测试；默认日程反馈策略通过，idle/一次性/迟做/错误开灯均失败。原始结果：`generated/case_contract_repair_v1/d0.json`；复现：`python tools/check_d0_case.py --output generated/NEW_DIRECTORY/d0.json`。新合同由pilot v1的D0评估分支使用；历史旧runner及其成绩不追溯改写。

本轮35项相关测试通过，包括完整时域、缺步、时钟、截止时刻、重复/无关事件不刷新宽限以及回家不抹除历史违规。这里只证明这条自编合同的限定可执行性/判分，不证明人类来源、泛化或LLM任务通过。

最新逐case数据核对由`case_review.py`维护，已接入页面；15条正式路线和BOPTEST均明确列出需求、判分对象、未解决问题及真实环境时域。后端交互验收不自动令case准入。现有案例仍是授权自编设计，不是开源人类需求来源。

本轮修复：IAQ改为不依赖未绑定占用窗口的全时段需求；双房间通风明确先恢复再维持；多楼明确为外部电表预算，不冒充原生供电容量；页面不再将旧接口摘要当作当前schema。共享通风的旧pilot判分改为实际模拟时间且要求完整原生轨迹，缺步/短轨迹/无时间/非有限读数返回未评估，中途违规不能靠终点恢复通过。其余旧pilot evaluator并未因此全部修复或获得正式准入，尤其电池终点判分、逐车离站与水系统服务合同仍待替换。

下文旧模型次数和设备失败归因属于历史；当前设备不可用是执行结果，不是JSON或纯接口合法性错误。浏览器原有case id及localStorage批注键未改变。

本目录包含 15 条正式 D0–D3 route 各一个人工设计的机制案例，以及 1 个尚未准入的 BOPTEST 候选案例。

- `viewer.html`：给人审阅的交互页面，可按层级筛选、搜索并在本地记录意见。
- `cases.js`：页面使用的结构化案例数据。
- `claim_designs.py`：按长期责任和论文机制重写的全后端设计源；`tools/build_claim_casebook.py` 生成 JSON 与页面覆盖层。旧案例 id 和浏览器批注键保持不变。
- `claim_designs.json`：15 条正式 route 加 BOPTEST 候选，每条列出 query、独立场景绑定、轨迹要求、机制对照、已有证据和未完成工作。设计覆盖不等于执行通过。

新页面不再把未验证设计标成“可支撑 claim”。主协议保留初始完整状态加无损增量；完整状态只用于诊断对照。

当前修正协议下已重新执行车库门案例：10 个环境步、11 次模型调用。模型最终关门，但再次受阻后多等待一步，违反一响应步的恢复要求。另一次请求在门不可用时尝试关门，被执行前校验拦截并纠正；这属于动作合法性错误，不是 JSON 格式错误。该实验只检验这一条案例，不能代表全后端已完成新一轮评测。

这些案例用于讨论 `自然长期 Query × 后端动态 × 轨迹级 evaluator` 是否对齐。它们不是开源语料中的真实用户原句，也不是已经由模拟器执行得到的 gold trajectory，不能直接当成最终 benchmark item。
