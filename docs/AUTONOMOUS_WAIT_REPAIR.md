# 自主等待修复与证据边界

## 主路径

`tools/run_trusted_llm_session.py` 使用的 `run_session` 现在默认启用自主等待，不是另一个未接入的试验运行器。原有 workflow 的 `for/until/until_event` 原生等待保持兼容。

模型输出示例：

```json
{"action": 0.5, "wait": {"mode": "for", "duration_seconds": 1800}}
```

仍使用外层 `<answer>...</answer>`。意思是使用指定控制，1800个模拟秒后再决策，而非每个内部步都询问模型。等待包括第一次执行动作的间隔，不是额外再加1800秒。内部步长不变，等待边界向上取整到原生步、终态截断。绝对等待使用 `{"mode":"until","time_seconds":...}`，这是episode已过秒数，不是现实时间。最长允许请求七天，实际到终态即停止。

事件等待使用 `{"mode":"until_event","timeout_seconds":1800,"observation_path":["battery_health","active"],"equals":true}`。仅按每个完成步的公开观测匹配标量值；字段不存在不匹配，不读取私有未来表，不自动额外唤醒。这个统一事件接口目前是公开字段相等条件，不宣称支持任意自然语言事件/阈值表达式。原生workflow事件过滤接口仍可单独使用，不能与外层wait嵌套。

连续控制在等待中保持模型指定的请求值，每个原生区间提交同一请求；这不是基于状态重新规划，也不是保证故障时实际输出不变。离散命令或规则操作只执行一次，后续为真正无命令等待。D0新增显式 `{kind:"wait"}`，不会用关灯冒充等待，也不会重复关门覆盖外生开门。`action:null` 表示不下新控制；连续后端在第一次明确控制之前拒绝它，不擅自选择零动作。

缺少wait的旧动作格式仍兼容一次原生操作，便于保留旧脚本，但模型提示明确要求自主选择wait。`autonomous_wait=False` 仅保留为固定步长诊断选项，不是CLI默认主协议。

## 轨迹与消耗

报告分别保存 `calls`（模型调用）、`decisions`（决策及其原生步区间）、`transitions`（每个完成的原生步）。一条decision可以对应多个transitions。每个内部回执仍写入落盘日志，即使等待中途出错也不丢弃已经执行的部分。

醒来时，一条环境反馈包含 `microsteps`：逐步公开回执、实际请求动作和无损观测增量。最后状态仍采用相对上次醒来状态的增量；不只展示终点，不删除期间已恢复的异常。完整内部轨迹保留给后续责任评估，等待不能豁免中间违规。模型等待期间不被调用，但状态增量并未有损压缩，所以没有事先承诺新的token成本。

只读 `tools/audit_real_sessions.py` 同时识别旧固定步长协议与新决策批次协议。新检查重新计算等待目标/唤醒条件、展开所有微步、核对模型动作与实际保持控制、重建每个观测；不依赖最终“通过”标签，也不将轨迹终止当成任务成功。

## 本地验证

- 108项相关单元/回归通过，包含短暂异常保留、事件提前唤醒、等待非法输入零副作用、首次纯等待不偷偷设置控制、D0不重复命令、旧workflow长等待兼容、篡改中间增量不能通过验收。D0旧“不允许wait”的测试更新为验证新公开wait合法、带多余字段的wait零副作用拒绝。
- `generated/autonomous_wait_native_v1/`：全部15条真实原生路由，一次脚本决策连续推进两个原生步。每条仅此限定范围检查，不是完整时域、不是实际LLM能力测试；外部API调用为0。报告的budget_exhausted是诊断按一次调用预算主动停止，不是后端失败或任务完成。
- 原来的13条完整LLM运行仍是固定步长历史证据，不能支持自主时间管理已通过。自主等待的真实模型完整运行和新的消耗结果尚待重测。
- 只读验收单列 `autonomous_verified_routes`，命令成功退出必须覆盖全部15条自主等待真实记录；旧固定步长记录即使齐全也不能通过这个交付门。

因此此前基于强制逐步问模型估算的约200MB调用计划不再直接执行；先验证正确交互机制，再按模型真实决策次数测消耗。未进入数据构造，也未宣布总体目标完成。

## 补充：故障穿越与完整长时域

原生电池对照：同一控制请求0.5，分别固定8次决策、一次等待到终态、在公开故障active时唤醒后再等待。三种方式的全部8条原生回执逐字段完全一致；事件模式在7200秒醒来，定时模式没有未经请求的故障自动唤醒，故障发生及恢复仍保留。这是脚本诊断，不是模型成绩。对应新增两项原生测试通过；本次相关组合41项通过。

全部微步和等待批次经独立重建核对，零外部API调用。这里没有把长时域缩短；只是把决策频率与模拟器步数解耦。终态完整历史分别约1.17MB、0.185MB；若下一次还需发送这些历史，则依旧受消息预算和模型上下文限制，不能声称长等待消除了所有上下文风险。脚本在终态不再调用模型，因此这次检查不证明LLM已读懂整段长反馈。

“模型必须选长等待”不是可信后端验收条件。必须验证的是它可合法选择时间、执行符合选择、期间物理轨迹真实且可评估；自然任务中的频率好坏需结合责任结果与消耗另行评测。
