Responsibility Benchmark

数据怎么来，
Agent 怎么被测

一套自顶向下的构造流程：从真实用户证据中归纳长期责任，再把责任绑定到可执行物理过程，最终放入闭环 harness 评测。

核心边界 责任由用户需求定义，不能从后端设备反推；后端只决定哪些责任目前能够形成可执行 Episode。

01 · 数据构造流程

上游保证责任有证据、Query 有人味；下游保证 Episode 可观察、可控制、可判分。

Corpus → Episode
1

真实用户证据

用户规则、访谈、日记与真实 Routine；保存原文、来源和限制。

2

AI 提取候选

高召回识别持续目标、受益人、触发、释放与失败意义。

3

责任准入

人工核对证据并去重；区分 responsibility type 与 scope/profile variant。

4

自然 Query

保留 source-near 表达，再生成多种语用改写并检查关键语义槽。

5

能力匹配

Contract 所需观测、动作、动力学、事件和 evaluator 与后端逐项匹配。

6

Episode 挖掘

扫描物理窗口，经可控性、语言敏感性、no-op/oracle 与泄漏门禁后发布。

02 · Episode 的两面

同一个 Episode 分成 Agent 可见面和私有评测面，避免把答案混进输入。

Information boundary

Agent View · 可以看到

  • 自然语言 Query 与用户明确表达的偏好
  • 完整场景设备清单、当前状态和公开事件
  • 安全边界、动作成本、cadence 与 horizon
  • 统一的 capability-family 合法动作 schema
  • 每步动作执行结果与新的增量观测

Private Evaluator · 不能看到

  • 标准责任 Contract、active mask 与评分实例
  • 未来天气、人员行为和完整物理轨迹
  • 窗口选择原因、source ID 与构造标签
  • witness、no-op、oracle 结果和最优动作
  • 责任偏差、安全偏差及 normalized gain

03 · Harness 是什么

Harness 是把 Agent、统一动作接口、物理后端和私有评分器接成可重复闭环的运行框架。

Observe → Act → Step → Score

Agent

读取 Query 与当前观测，决定操作哪些设备；也可以明确 no-op。

{"commands":[ {"device_id":"kitchen_hvac_1", "capability":"thermal_control", "operation":"set", "parameters":{"mode":"heat","target_c":22}} ]}
⇄

Harness Runtime

  • 校验动作：无默认值、无越权、原子执行
  • 适配动作：翻译到 SimuHome / EnergyPlus / CityLearn / EV2Gym
  • 推进时间：按固定 cadence 运行物理过程
  • 返回观测：设备状态、环境变化和错误反馈
  • 记录轨迹：输入、动作、执行结果和版本哈希
→

Private Evaluator

  • protocol validity
  • safety / responsibility deviation
  • action 与无关干预成本
  • 相对 no-op / oracle 的 normalized gain
  • Query 删除与 shuffle 诊断

04 · Episode 准入门

不是“模拟器能跑”就进入 benchmark；每条 Episode 必须证明动作和语言都真正有用。

Fail closed
可观察合理决策所需信息对 Agent 可见
可控制合法动作能够改变责任结果
有机会差oracle 明显优于 no-op
语言敏感删除或打乱 Query 会改变策略
无泄漏输入中没有 Contract、目标或未来答案
